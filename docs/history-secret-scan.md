# Git history and working-tree secret scan

Rechecked 28 October 2026 after rewriting the nine GitHub branch heads. The local clone scanned 150 reachable commits and 13 local/remote-tracking refs, plus readable working-tree files, including ignored files. `npm run audit:history-secrets` applies pattern-based checks for AWS access key IDs, GitHub tokens, private-key headers, JWT-like tokens, database URLs containing credentials, and long secret assignments. It reports locations and token metadata only; it never prints matched values. It skips `.git` during the working-tree scan, dependency/browser/build output directories, binary files, and files larger than 50 MiB.

## Findings

- No configured patterns matched the current readable working tree or the rewritten branch/tag history. Before the rewrite, the scan found 24 repeated JWT-like matches in older versions of `src/integrations/supabase/client.ts`; they were one historical `anon` client key, not 24 distinct credentials. The replacement scrubbed JWT-like values from all nine remote branch histories while preserving their source files and commits. No key value or project reference is copied into this report.
- No matches were found for the configured AWS, GitHub-token, private-key, credentialed-database-URL, or long-secret-assignment patterns.

The active application has had its database client, account pages, schema, migrations, and CI database job removed. The nine branch heads were rewritten, and a follow-up local scan found zero matches in 150 reachable commits; `git fsck --no-reflogs --unreachable` also found no unreachable objects in the active clone. This does not revoke the old key or delete the matching hosted project.

GitHub's read-only closed pull-request refs `refs/pull/1/head` through `refs/pull/8/head` still point to their old commit hashes. The open PR #9 head and merge refs now use rewritten commits. Therefore the historical client key may remain visible in closed PR diffs or cached commit views even though normal branch history is clean. The repository had zero forks at the time of the rewrite, but other clones cannot be cleaned remotely. GitHub documents that cached views and pull-request refs may require a GitHub Support request; none has been submitted. Support may not purge a public `anon` client key because it is not a privileged credential. Do not describe the external key as revoked or the repository as fully purged.

The owner restored the downloaded database backup locally and reported 29 non-system tables. The five former application tables (`public.billing`, `public.energy_usage`, `public.payments`, `public.profiles`, and `public.sockets`) each had zero rows; `auth.users` had four rows; `storage.objects` had zero rows. A privacy-minimizing aggregate check found four email-provider identities, three confirmed accounts, two accounts with a recorded sign-in, and no obvious test/placeholder patterns in the email local-part or common reserved test domains. The individual emails and metadata were not printed or reviewed. These signals do not prove whether the accounts are real or test accounts; treat them as possible personal data until the owner reviews them. The separately downloaded Storage-objects archive has not been located or inspected. Auth configuration, policies/grants, logs, functions, secrets, and retention are also unreviewed. This is evidence about that local backup only, not a live-project key-status check.

The Supabase dashboard says the project was paused for more than one year and cannot be resumed from Studio. Supabase documents a one-year self-service restore window and recovery from available backups after that window. Creating a replacement project gives it new keys and a new project reference; it does not revoke the key in the old project. The four Auth records are not yet safely classifiable as disposable demo users, and the separate Storage archive remains unreviewed. Treat both as possible personal data until reviewed and retained or securely discarded by the owner.

To address the old legacy key, the owner can still try **Settings → API Keys** in the original project or the Management API alternative: `PUT https://api.supabase.com/v1/projects/{ref}/api-keys/legacy?enabled=false`. It requires an owner/admin Management API token with `api_gateway_keys_write` permission (the fine-grained OAuth scope is `secrets:write`), and disables the legacy `anon` and `service_role` keys together. The paused project is currently inaccessible to the owner, so its key status remains unconfirmed; this repo cleanup is not a substitute for deactivation. Do not put a token in Git, a shell transcript, or chat. Only delete the old project after the database and Storage backups have been reviewed and data to retain has been secured; deletion permanently removes its remaining data and backups.

## Limits

This is a targeted pattern scan, not a guarantee that no secrets exist. It does not inspect GitHub issues, pull request comments, uploaded attachments, inaccessible refs, external hosted-project state, local files above 50 MiB, or encrypted/binary files. Run an organization-approved dedicated secret scanner and review any alerts before a sale or transfer. Keep repository visibility unchanged until the project and ownership reviews are complete.
